# Feature Specification: Kubernetes 장애 감지 및 AI 진단

**Feature Branch**: `main` (명세 작성 시점)

**Created**: 2026-11-27

**Status**: Draft

**Input**: 로컬 k3d에서 컨테이너 장애를 재현하고, 실시간으로 접수하며,
AI 진단 리포트를 담당자가 승인한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 테스트 장애 재현 (Priority: P2)

운영자는 `target-apps`의 `chaos-app`에서 세 가지 테스트 장애를 개별적으로
재현해 감지와 진단을 검증할 수 있다.

**Why this priority**: 반복 가능한 장애가 있어야 탐지와 진단을 같은 조건에서 비교할 수 있다.

**Independent Test**: 수집과 진단 서비스를 중지한 상태에서 각 시나리오를 실행한다.

**Acceptance Scenarios**:

1. 메모리 시나리오를 실행하면 대상 컨테이너의 종료 사유가 `OOMKilled`이고 종료 코드가 137이다.
2. 잘못된 설정 시나리오를 실행하면 대상 컨테이너가 반복 재시작하여 `CrashLoopBackOff`에 도달한다.
3. HTTP 시나리오를 실행하면 테스트 요청에 500 응답이 발생하고, 이를 관측하여 급증 조건을 재현할 수 있다.

### User Story 2 - 실시간 감지와 중복 없는 접수 (Priority: P1)

운영자는 대상 네임스페이스의 장애가 발생하면 진단 진행 여부와 관계없이 접수 결과를 확인할 수 있다.

**Why this priority**: 접수된 장애는 진단 서비스가 일시 중단되더라도 추적할 수 있어야 한다.

**Independent Test**: 진단 워커를 멈추고 대상 Warning, OOMKilled 종료 상태, HTTP 5xx 급증을 각각 관측한다.
같은 이벤트를 동시에 재전송하고 다른 네임스페이스의 Warning도 관측한다.

**Acceptance Scenarios**:

1. 대상 Warning이 관측되면 `event-watcher`가 웹훅을 보낸다. 새 장애는 `OPEN`으로 저장되고,
   진단 작업이 발행된 직후 발신자가 `202 Accepted`를 받는다.
2. 대응하는 Warning이 없어도 대상 컨테이너의 OOMKilled 종료 상태를 관측하면 같은 방식으로 접수된다.
   HTTP 5xx 급증이 설정된 조건을 충족한 경우에도 같은 접수 흐름으로 들어간다.
3. 동일 이벤트를 정상 접수 후 반복 또는 동시에 전달해도 티켓과 논리적 진단 작업은 각각 하나다.
   다른 네임스페이스의 Warning은 접수 대상에서 제외된다.

### User Story 3 - 근거가 있는 AI 진단 (Priority: P2)

담당자는 장애 티켓에서 추정 원인, 관측 증거, 매뉴얼 인용, 검토할 YAML 패치를 확인한다.

**Why this priority**: 담당자는 원인과 조치 제안을 근거까지 추적하고 검토할 수 있어야 한다.

**Independent Test**: 알려진 원인의 `OPEN` 티켓과 진단 작업을 준비하고, 로그와 문서 자료를
제공한 상태에서 진단을 실행한다.

**Acceptance Scenarios**:

1. 워커가 작업을 소비하면 `k8s_inspector`로 대상 Pod의 최근 로그, Kubernetes 이벤트,
   컨테이너 종료 코드 및 리소스 Limit을 조회하고, `runbook_rag`로 과거 회고록과
   트러블슈팅 매뉴얼에서 유사 사례를 검색한다.
2. 충분한 근거가 있으면 추정 원인, 확인 가능한 문서 인용, 권장 YAML 패치를 포함한
   리포트가 티켓에 저장되고 상태가 `NEEDS_REVIEW`로 바뀐다.
3. Pod가 사라졌거나 관련 문서를 찾을 수 없으면 리포트에 누락된 근거와 진단 한계를 표시한다.
   근거가 부족해 패치를 제안할 수 없으면 그 이유를 표시한다.

### User Story 4 - 담당자 승인 (Priority: P2)

지정된 담당자는 진단 리포트를 검토하고 승인하여 티켓의 진단을 확정한다.

**Why this priority**: 담당자가 진단의 정확성과 제안된 조치의 적절성을 확인한다.

**Independent Test**: 리포트가 있는 `NEEDS_REVIEW` 티켓으로 권한 있는 담당자와
권한 없는 사용자 각각의 승인 요청을 시험한다.

**Acceptance Scenarios**:

1. 담당자가 `POST /incidents/{id}/approve`로 승인하면 상태가 `APPROVED`로 전환되고
   승인자와 시각이 기록된다. 워크로드 설정은 그대로 유지된다.
2. 미승인 권한으로 요청하거나 `OPEN` 상태에서 승인하면 요청이 거부되고 티켓이 유지된다.
   동일한 승인 요청을 재시도하면 최초 승인 기록이 유지된다.

### Edge Cases

- 티켓 저장 또는 작업 발행에 실패하면 새 요청에 `202`를 반환하지 않는다.
  발행이 불확실하거나 실패한 뒤 재전송해도 기존 티켓을 복구해 발행을 완료할 수 있어야 한다.
- 하나의 Warning 이벤트가 반복 관측되어도 동일 이벤트 식별자를 유지한다.
  같은 Pod 이름의 새 인스턴스나 독립적으로 관측된 새 이벤트는 별도 장애로 접수할 수 있다.
- 진단 작업이 재전달되거나 늦게 완료되어도 중복 리포트 생성이나 승인 상태의 역행을 방지한다.
- 일시적인 도구 호출 실패는 정상적인 빈 검색 결과와 구분한다. 진단 실행 자체가 실패하면
  티켓을 `OPEN`으로 유지하고 재시도 가능한 실패로 기록한다.
- 종료 이력이 없는 컨테이너의 종료 코드는 해당 없음으로, 수집할 수 없는 값은 확인 불가로 표시한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `chaos-app`은 `target-apps`에서 테스트 운영자가 OOMKilled(종료 코드 137),
  잘못된 설정으로 인한 CrashLoopBackOff, HTTP 500 폭주를 개별적으로 유발할 엔드포인트를 제공해야 한다.
  재현은 로컬 테스트 워크로드 범위로 제한한다.
- **FR-002**: `event-watcher`는 `target-apps`의 Warning 이벤트를 관측해
  `aiops-api`의 `POST /incidents`로 웹훅을 보내야 한다. 신호에는 안정적인 이벤트 식별자,
  발생 시각, 네임스페이스, 대상 워크로드 및 장애 유형을 포함해야 한다. OOMKilled 종료 상태는
  대응하는 Warning이 없는 경우에도 감지해야 하며 같은 종료가 두 신호로 관측되면 한 번만 접수한다.
- **FR-003**: 시스템은 대상 워크로드에서 관측한 HTTP 5xx가 설정된 관측 구간과 임계값을
  충족하면 급증 신호를 만들고 동일 접수 흐름으로 전달해야 한다.
- **FR-004**: 접수 서비스는 이벤트 식별자로 중복을 판정해야 한다. 새 이벤트에 대해 PostgreSQL에
  `OPEN` 티켓을 저장하고 Valkey Streams에 진단 작업을 발행한 직후 `202 Accepted`를
  반환해야 한다. 같은 이벤트는 기존 티켓으로 연결하고 발행이 완료된 작업을 다시 생성하지 않는다.
- **FR-005**: Hot Path에서 직접 LLM 또는 MCP 호출과 동기 폴링을 금지한다.
  저장 또는 발행이 완료되지 않으면 접수 실패를 알려야 하고, 재시도는 티켓과 논리적 작업을
  하나씩만 남겨야 한다.
- **FR-006**: `aiops-worker`는 비동기로 작업을 소비하고, `k8s_inspector`와
  `runbook_rag`를 호출해야 한다. 조사 대상과 조회 결과는 해당 티켓에 연결해야 한다.
- **FR-007**: 진단 리포트는 추정 원인, 관측 증거, 관련 문서 인용과 추적 가능한 출처,
  권장 YAML 패치를 담아야 한다. 확인 불가 항목은 이유와 함께 표시하고, 증거가 부족한 경우
  확인 가능한 사실과 추정을 구분해야 한다.
- **FR-008**: 리포트 저장과 `OPEN → NEEDS_REVIEW` 전이는 함께 완료되어야 한다.
  재전달된 작업은 검토 중이거나 확정된 리포트와 상태를 덮어쓰지 않아야 한다.
- **FR-009**: `POST /incidents/{id}/approve`는 승인 권한이 있는 담당자의
  `NEEDS_REVIEW → APPROVED` 전이와 승인 이력 기록을 지원해야 한다. 이미 처리한 동일
  승인은 같은 결과를 반환하고, 존재하지 않는 티켓 또는 허용되지 않은 상태의 요청은 거부해야 한다.
- **FR-010**: `mcp-server`의 Kubernetes 권한은 `pods`, `pods/log`, `events`에 대한
  `get`, `list`, `watch`로 한정해야 한다. 티켓 승인은 리포트를 확정한다.
  실제 패치 적용은 담당자의 명시적인 승인과 별도 실행이 필요한 범위다.
- **FR-011**: 로컬 검증 환경은 16GB RAM 예산을 준수해야 하며, 모든 Deployment의
  각 컨테이너에 리소스 요청과 한도를 명시해야 한다.

### Key Entities

- **장애 신호** — 이벤트 식별자, 발생 시각, 대상 워크로드, 장애 유형, 관측 내용.
- **인시던트 티켓** — 티켓 ID, 원본 이벤트, 상태, 리포트와 승인 이력 참조.
- **진단 작업** — 티켓 참조와 처리 상태를 갖는 비동기 작업.
- **진단 리포트** — 추정 원인, 관측 증거, 문서 인용, 권장 패치, 확인 제약.
- **승인 기록** — 승인된 티켓과 리포트, 승인자, 승인 시각.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 준비된 로컬 검증 환경에서 장애 유형별 10회씩 총 30회 재현할 때 전체의 95% 이상이 해당
  감지 신호가 관측 가능해진 시점부터 30초 안에 접수된다.
- **SC-002**: 진단 서비스를 중지한 상태에서도 유효한 신규 웹훅 30건 중 95% 이상이
  요청 후 1초 안에 접수 응답을 받고, 각 이벤트를 5회 재전송해도 티켓은 이벤트당 1개다.
- **SC-003**: 알려진 원인과 관련 문서가 있는 대표 시나리오 3종 모두에서 접수 후 2분 이내에
  올바른 추정 원인, 담당자가 확인할 수 있는 문서 인용, 검토 가능한 권장 패치를 제공한다.
- **SC-004**: 승인 검증에서 권한 있는 담당자가 제출한 유효한 요청 10건 모두가
  최초 승인자와 시각을 보존한 상태로 확정된다. 권한 없는 요청과 상태가 잘못된 요청에서는
  확정이 0건이며, 승인 과정에서 워크로드 설정 변경도 0건이다.

## Assumptions

- 대상은 로컬 k3d의 `target-apps`이며, 프로젝트 헌법의 네임스페이스와 예산을 따른다.
- HTTP 500 응답은 그 자체로 Kubernetes Warning 이벤트가 되지 않으므로 5xx 관측 신호가 필요하다.
  초기 검증 기준은 30초 내 5xx 응답 10건으로 가정한다. 구체적인 관측 구성은 설계 단계에서 정한다.
- 운영자가 검증 전에 대표 회고록과 매뉴얼을 준비한다. 관련 문서가 없을 때의 동작도 별도로 검증한다.
- 최종 확정 상태 이름은 `APPROVED`로 가정한다. 승인 권한은 지정된 담당자에게 부여하며,
  구체적인 인증 방식은 설계 단계에서 정한다.
- 시간 목표는 운영 SLA가 아닌 로컬 검증용 초기 수용 기준이다.
